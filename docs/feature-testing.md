# 주요 기능 확인

개발 서버에서 로그인 화면의 **주요 기능 테스트**를 누르면 `/dev/tools`가 열린다. 내 정보와 각 화면 상단에서도 돌아올 수 있다. 테스트 화면은 `.env`의 `VITE_API_URL`을 사용하는 실제 API 화면이다. 토큰이나 상대방의 확인 상태를 임의로 만들지 않는다.

사장님 이름과 청년 이름을 따로 입력하고 **사장님으로 보기**, **청년으로 보기**로 바꾼다. 기본 계정은 김순자·이도윤이다. 기존 계정의 진행 상태가 이미 달라졌다면 새로운 테스트 이름 두 개로 등록부터 시작할 수 있다. 현재 승계의 두 사람 이름을 확인하고, 그 상대방 계정으로 바꿔야 같은 승계를 이어서 확인할 수 있다. **상대방 이름 채우기**는 입력란만 채우며 로그인·승인을 실행하지 않는다.

기본 정보가 없으면 이름·나이를 먼저 확인한다. 사장님은 가게와 금액·물려줄 것·은퇴일을, 청년은 경력·자금·대출·희망 조건을 저장한다. 그 뒤 테스트 화면으로 돌아온다. 새 계정의 등록이나 제안 수락·승인 등은 직접 버튼을 누른 경우에만 실제 서버에 저장된다.

| 순서 | 확인할 사람 | 확인 방법과 결과 |
| --- | --- | --- |
| 1. 등록·수정 | 각각 | 가게 또는 청년 조건을 저장하고 다시 열어 저장값을 확인한다. |
| 2. 추천·제안 | 사장님 | 청년 찾기에서 실제 후보의 점수·이유를 보고 제안한다. 보낸 제안의 대상·가격·문구를 확인한다. |
| 3. 제안 수락 | 청년 | 받은 제안을 열고 수락한다. 서버가 승계를 만들고 일정·체크리스트가 열린다. 거절·철회는 수락 전 별도의 테스트 제안으로 확인한다. |
| 4. 일정 변경 | 한 사람 → 상대방 | 은퇴일 변경을 요청한다. 요청한 사람에게는 답변 대기가, 상대방에게는 승인·거절이 보이는지 확인한다. 승인 후 바뀐 일정을 다시 조회한다. |
| 5. 체크리스트 | 각각 | 각 항목에 메모와 본인 확인을 남긴다. 본인 확인 취소도 시험한다. 두 사람이 모두 확인한 항목만 완료로 집계되고 전체 완료 시 계획 단계로 진행한다. |
| 6. 계획 | 각각 | 초안을 만들고 항목을 고친다. 수정자·내용·동의 상태를 확인한 뒤 두 사람이 동의한다. 생성 결과에 따라 AI 초안 또는 기본 초안으로 표시한다. |
| 7. 수습 로드맵 | 청년 → 사장님 | 청년이 현재 단계의 일을 완료 요청한다. 사장님은 이유를 적어 다시 해 보기를 요청한다. 청년이 재요청하면 사장님이 승인한다. 현재 단계의 모든 일을 승인하면 다음 단계가 열리고, 3단계 9개를 마치면 운영권 인수로 진행한다. |
| 8. 납입 | 청년 → 사장님 | 청년이 항목·납입일·메모를 기록한다. 사장님이 수령을 확인한다. 확인된 금액·남은 금액·진행률이 반영되는지 본다. 수습과 필요한 납입을 모두 마치면 승계 완료를 확인한다. |

다른 역할이나 다른 탭에서 처리한 뒤에는 **최신 진행 상황 확인**, **상대방 확인 내용 새로 보기**, **최신 납입 내용 확인**, 테스트 화면의 **새로 확인**으로 다시 읽는다. 테스트 화면은 실제 체크리스트 수·양쪽 동의·로드맵 과제 수·납입 횟수를 집계한다. 조회 실패는 해당 기능 이름과 오류로 표시하고 다시 조회할 수 있다.

## 받은 제안 바로 보기

사장님이 제안을 보낸 뒤 **○○ 님으로 받은 제안 보기**를 누르면 그 청년 계정으로 전환해 같은 제안을 연다. 주요 기능 테스트의 보낸 제안 목록에도 같은 버튼이 있다. 서버가 발급한 계정 ID가 실제 수신 청년 ID와 같은지 먼저 확인하고 세션을 바꾼다. 이 전환은 수락하지 않으며, 청년 화면에서 내용과 확인 창을 보고 **수락하기**를 따로 눌러야 한다.

일반 청년 화면에서는 홈 맨 위 **받은 승계 제안 → 제안 확인하고 답하기**, 또는 하단 **승계 교육**으로 들어간다. 수락 후 **승계 과정**에서 일정·체크리스트·계획·로드맵을 확인하며, 홈에도 **승계 과정 이어보기**와 **수습 로드맵 보기**가 표시된다. 로드맵이 아직 없으면 양쪽 체크리스트·계획 동의를 먼저 안내한다.

## 로드맵 연결 근거

- 조회: `GET /api/successions/{sid}/roadmap`
- 청년 완료 요청: `POST /api/successions/{sid}/roadmap/tasks/{taskId}/request`, 선택 메모 `memo`
- 사장님 승인: `POST /api/successions/{sid}/roadmap/tasks/{taskId}/approve`
- 사장님 다시 해 보기: `POST /api/successions/{sid}/roadmap/tasks/{taskId}/send-back`, 필수 이유 `reason`

계획에 양쪽이 동의하면 서버가 로드맵·납입표를 생성한다. 서버가 현재 단계로 반환한 일만 역할과 상태에 맞게 조작한다. 프런트에서 날짜나 상태를 바꿔 로드맵을 강제로 열지 않는다.

2026-11-08 배포 서버 명세와 위 4개 경로가 일치함을 확인했다. 당시 김순자·이도윤 계정은 등록은 되어 있지만 `successionId=null`, 현재 승계 조회 404였으므로 로드맵을 확인하려면 제안 수락부터 진행해야 했다. 이후의 서버 데이터는 **새로 확인**으로 조회한다. 실제 서버의 완료 요청·승인 성공을 이미 확인했다고 간주하지 않는다.

## 코드 검증

`npm run test:api`는 실제 API 모듈을 실행하되 모든 네트워크 응답을 가로채어 요청 URL·메서드·본문·계정 토큰·오류 처리를 확인한다. 최신 OpenAPI에 존재하는 메서드인지도 검사한다. 실서버에 업무 데이터를 쓰지 않는다. 실제 화면의 상태 전환은 격리된 테스트 서버로 별도 검증하며 실서버 검증과 구분한다.

2026-11-08 검증 결과: API 요청·인증·오류 45개, 모의 브라우저 주요 기능 36개 통과. 브라우저에서 제안부터 6개 양쪽 체크·상호 동의·3단계 9개 수습 승인·4회 납입 확인을 거쳐 `COMPLETED`와 잔액 0까지 진행했다. 제안 거절/철회·일정 변경·재수행·요청 실패 후 재시도·대시보드 부분 조회 실패 복구도 포함한다. 실제 배포 서버의 업무 데이터를 바꾸지 않았다.
