# 백엔드 연결 상태

확인일: 2026-11-08. 사용자가 제공한 OpenAPI v1을 [openapi.json](openapi.json)에 보존했다. 첨부 텍스트에서 JSON 뒤의 일반 문장은 제외했으며, 실제 배포 서버의 `GET /v3/api-docs`와 경로·스키마가 같은 것을 확인했다.

## 연결 범위

| 화면·기능 | API와 동작 |
| --- | --- |
| 로그인·역할 | 카카오 시작·토큰 콜백·`GET /api/me`·`PUT /api/me/role`을 연결했다. 현재 배포 서버의 카카오 시작 주소가 404라 백엔드 설정이 필요하다. 휴대폰은 버튼만 표시하고 비활성화한다. 개발 서버에서만 이름 기반 시연 로그인을 별도로 제공한다. |
| 개발용 주요 기능 테스트 | `/dev/tools`에서 역할별 계정 전환·실제 서버 상태·선행 조건·기능별 진입을 제공한다. 조회 실패는 기능별로 구분하며 단계·승인·납입을 자동 완료하지 않는다. |
| 로그아웃 | `POST /api/auth/logout`. 성공 후 현재 토큰·계정 보조 정보·입력 초안을 비우고 비공개 화면 재진입을 막는다. 네트워크 오류면 오류를 표시하고 재시도한다. |
| 온보딩 | 역할 선택 → 이름·나이 → 가게/청년 조건 → 서버 저장 성공 후 홈. 저장 실패 시 입력을 유지한다. |
| 가게·청년 등록 | 본인 정보 GET/PUT. 기존 정보 조회 실패 시 기본값으로 덮어쓰지 않고 재시도한다. 금액·나이·날짜·수습 기간을 검증한다. |
| 홈·가게 탐색·청년 매칭 | `GET /api/youth/matches`의 실제 가게·점수·점수 항목·추천 이유를 표시한다. 반환된 최대 20곳에 검색·업종 필터를 적용한다. |
| 사장님 가게·청년 찾기 | `GET /api/owner/shop`, `GET /api/owner/matches`. 가게 보기 탭은 사장님 본인 가게만 표시한다. |
| 제안 | 목록·개별 상세 GET, 사장님 POST 제안·철회, 청년 POST 수락·거절. URL의 제안 ID로 정확한 제안을 조회한다. |
| 받은 제안 진입 | 청년 홈에 받은 제안·현재 계정·전체 과정 진입을 표시한다. 개발용 보낸 제안에서 실제 수신 청년 ID를 확인해 같은 제안으로 전환한다. 수락 후 전체 과정으로 이동하고, 후속 조회가 실패해도 성공한 수락을 다시 제출하지 않게 한다. |
| 교육·진행 상황 | 서버의 현재 승계 요약·진행률·할 일을 표시한다. 제안 수락 전 교육 진행을 만들지 않는다. |
| 일정 | 조회·변경 요청·상대방 승인/거절. 서버의 일정을 사용한다. |
| 체크리스트 | 본인 확인·취소·선택 메모. 상대방 대신 확인하는 동작은 없다. |
| 계획 | 초안 생성·항목 수정·수정 이력·각자 동의. 서버 `generatedBy`가 AI/TEMPLATE 중 무엇인지 표시한다. 체크리스트 완료 전 동의를 막고, 이후 단계에서는 읽기 전용으로 표시한다. |
| 수습 | 청년 완료 요청과 메모, 사장님 승인·필수 이유를 담은 다시 해 보기. 역할·현재 단계·상태에 맞는 버튼만 표시한다. |
| 납입 | 청년 납입 기록·사장님 수령 확인. 실제 송금이나 결제 API가 아니다. |

## API에 없는 정보

- 사진 업로드 API가 없다. 사용자 사진은 현재 브라우저의 미리보기이며, 기본 사진은 출처를 기록한 CC0 분위기 참고 자료다.
- 전체 공개 노포 검색·가게 역사·메뉴 가격 API가 없다. 임의의 가게·역사·메뉴 가격을 실제 데이터처럼 표시하지 않는다.
- 연락처·이메일·사장님 나이 수정 API가 없다. 해당 값은 현재 브라우저 탭의 계정별 보조 정보다. 이름은 카카오 로그인 정보를 읽기 전용으로 표시하며, 개발용 확인에서만 시연 계정 이름을 변경할 수 있다. 청년 나이는 실제 청년 프로필에 저장한다.
- 대화 메시지 API가 없다. 이전 브라우저 전용 대화 제안 기능을 제거하고 실제 계획 항목 수정으로 연결했다.

## 명세의 중복 이름

OpenAPI의 `ChecklistResponse.items`가 일정용 `Item` 스키마를 가리키는 이름 충돌이 있다. 실제 [ChecklistResponse.java](https://github.com/donghyun-03/mullyeobatgi-backend/blob/main/src/main/java/com/danditon/mullyeobatgi/checklist/ChecklistResponse.java)의 항목은 다음과 같다.

`id`, `seq`, `code`, `title`, `description`, `ownerConfirmed`, `ownerConfirmedAt`, `ownerNote`, `youthConfirmed`, `youthConfirmedAt`, `youthNote`, `done`, `confirmedByMe`.

화면은 위 실제 DTO를 사용하며 일정용 항목과 혼용하지 않는다.

## 직접 확인

1. 프로젝트 터미널에서 `npm run dev`를 실행하고 `http://localhost:5173`으로 접속한다. 서버가 이미 켜져 있으면 해당 주소를 새로고침한다.
2. 카카오 로그인의 서버 설정은 [auth-setup.md](auth-setup.md)를 참고한다. 서버 설정 전 화면 확인은 개발 서버의 `개발용으로 확인하기` → 역할 선택 → 기본 정보로 진행한다. 명세의 기존 시연 계정은 사장님 `김순자`, 청년 `이도윤`·`박서연`·`최민재`다.
3. 새 이름은 새 시연 사용자를 만든다. 실제 서버에 연결되어 있으므로 화면에서 등록·제안·수락·승인한 내용은 서버에 저장된다.
4. 개발용 확인에서는 기본 정보의 뒤로 버튼 또는 내 정보의 `다른 역할로 확인하기`로 역할 선택에 돌아가 두 역할을 번갈아 확인한다. 사장님·청년은 별도 개발 계정으로 로그인하며 계정의 실제 역할을 바꾸지 않는다. 각 역할의 마지막 시연 이름을 기억하고 저장한 정보를 다시 불러온다.
5. 주요 기능은 로그인·내 정보의 `주요 기능 테스트`로 확인한다. 상세 순서는 [feature-testing.md](feature-testing.md)를 참고한다. 로드맵은 제안 수락·체크리스트·계획 양쪽 동의 뒤에 서버가 생성한다. 2026-11-08 실서버 재조회 당시 기본 시연 계정에는 아직 진행 중인 승계가 없었다.

## 검증

- 실제 배포 서버의 명세·CORS, 기존 시연 계정 로그인·본인 정보·가게·청년 후보/가게 후보·제안 목록 조회·로그아웃을 확인했다. 기존 시연 가게·제안·승계 데이터는 수정하지 않았다.
- 상태 변경 요청의 URL·메서드·본문·인증·오류 처리는 로컬 응답으로 검증한다. 등록·수락·승인 전체 흐름은 배포 서버 데이터에 영향을 주지 않는 테스트 API를 사용한다.
- 최종 결과: API 요청 형식 30개, 실제 서버 브라우저 조회·로그인·로그아웃 31개, 테스트 서버의 등록·제안·승계·오류 복구 43개 검증이 통과했다. 320px·390px에서 하단 메뉴와 주요 버튼이 겹치지 않음을 확인했다.
- 실제 서버 검증 중 CORS 오류·실행 오류·가게/제안/승계 쓰기 시도는 0개였다. 로그아웃 후 잘못된 화면으로 이동하던 문제를 수정하고 두 환경에서 다시 확인했다.
- `npm run build`와 `git diff --check`를 통과했다. 변경은 로컬 작업 트리에 두며 이번 요청에서는 새 커밋·push·PR·배포를 하지 않았다.
- GitHub push·PR 생성·사이트 배포는 사용자 확인 전 진행하지 않는다.
- 카카오 화면 복구 이후 인증 wire 12개와 모의 브라우저 인증·기존 계정 온보딩 30개를 추가로 검증했다. 실제 카카오 시작 경로는 현재 404이며 프런트 콜백 구현 검증과 실제 공급자 로그인 성공을 구분한다.
- 개발용 역할 전환 인증 요청 7개를 추가 검증했다. 역할 미선택 계정은 발급받은 새 토큰으로 역할을 확인한 뒤 세션을 교체하며, 서버 오류·역할 불일치·네트워크 실패는 기존 세션을 유지한다.
- 개발용 전환 모의 브라우저 27개가 통과했다. 사장님↔청년 왕복·정보 분리/복원·실패 후 재시도·새로고침·내 정보 전환·카카오 역할 잠금·운영 빌드 차단을 확인했다. 자동 가게/청년/제안 저장과 실제 서버 요청, 실행 오류는 없었다.
- 재실행 가능한 `npm run test:api`의 요청·인증·오류 45개 검증이 통과했다. 정상 요청 33개 메서드·경로를 최신 OpenAPI와 대조하고, 제안 수신자 ID 확인 후 세션 전환도 검증한다. 실제 서버 쓰기는 없다.
- 주요 기능 모의 브라우저 검증 36개가 통과했다. 제안 철회·거절·수락, 일정 변경 거절/승인, 6개 양쪽 체크·취소·메모, 계획 생성·수정·동의 초기화·상호 동의, 수습 3단계·9개 일의 요청/반려/재요청/승인, 납입 4회 기록/수령 확인 → 완료·잔액 0까지 화면으로 확인했다. 단계 전환은 모의 서버가 각 역할의 실제 요청 순서로 계산했으며 프런트의 강제 완료는 없다. 대시보드 일부 조회 실패·복구와 320px/390px 너비도 확인했다. 실행 오류·실서버 업무 요청은 0개였다.
- 받은 제안 진입 모의 브라우저 17개가 통과했다. 기억한 청년과 다른 실제 수신자로 전환, ID 불일치 시 기존 인증 보존, 같은 제안 수락 → 전체 과정, 수락 성공 후 조회 실패 시 중복 수락 방지, 홈 제안·진행 카드, 로드맵 선행 조건·만료 제안 제외·320px/390px 화면을 확인했다. 실서버 요청과 실행 오류는 0개였다.
