## 서비스와 디자인

물려받기는 문 닫을 대구 노포의 맛과 단골을 청년이 이어받도록 돕는 승계 서비스다.

- 사장님: 가게를 물려주는 사람.
- 청년: 가게를 이어받는 사람.
- 기본 진입 흐름: 로그인 → 역할 선택 → 이름·나이 등 기본 정보 → 역할별 가게·매칭 조건 → 홈. 사람 찾기와 제안은 온보딩을 마친 뒤 시작한다.
- 로고: 굵은 남색 글자와 하늘색 점으로 ‘물려’와 ‘받기’를 연결. 앱 아이콘과 앱 상단에 사용.
- 화면 디자인은 기존 `src/pages/LoginPage.css`와 `src/styles/global.css`의 글꼴, 색상, 공통 버튼·앱 셸 스타일을 기준으로 맞춘다.

## API 공통 규칙 - PDF

- 로그인·로그아웃을 제외한 API는 로그인 토큰이 필요하다. 토큰 전달 형식은 문서에 없다.
- 금액은 모두 **만 원 단위**다.
- `{sid}`는 청년이 제안을 수락하면 생성되는 **승계 ID**다.
- `GET /api/me`에서 내 정보, 역할, 등록 여부, 진행 중인 승계를 확인해 진입 화면을 고른다.
- 사용자 요구사항의 로그인은 카카오·휴대폰 방식이지만, PDF에 명시된 로그인 API는 개발용 로그인뿐이다. 실제 카카오·휴대폰 인증 API는 별도 확인이 필요하다.

## 구현 시 구분할 사항

- 화면 요구사항과 API 지원 범위를 구분한다. 화면 설명에 있는 항목의 JSON 필드가 PDF에서 확인된 것은 아니다.
- PDF만으로 서버 주소, 요청·응답 JSON, 역할 값, 상태 값, 오류 응답, 토큰 전달 방식을 확정할 수 없다. 이후 제공된 백엔드 소스에서 확인한 내용은 아래 최신 맥락을 참고한다.
- 초기 작업의 프런트 경로는 `/`(로그인), `/role-select`(역할 선택)이었다. 이후 팀원 브랜치를 기준으로 전환했으며 현재 역할 선택 경로는 `/role`이다.
- 이 기록만으로 추가 화면이나 API 연동이 구현되었다고 간주하지 않는다.

- 팀원 코드의 프런트 역할 값은 `owner`·`successor`다.
- 사용자가 추가로 제공한 5개 화면: 사장님 은퇴 희망일(4/5), 청년 경력·자금·조건(2/3), 사장님 매칭, 청년 받은 제안, 승계 가일정.
- **최신 디자인 지시:** 사진은 구성 참고 자료다. 완전히 동일하게 만들 필요는 없으며 깔끔한 여백과 읽기 쉬운 화면을 우선한다. 사진의 무채색 대신 기존 LoginPage의 남색·하늘색 토큰을 사용한다.
- 사장님은 `/owner` → `/owner/shop`(가게 정보, 1/3) → `/owner/terms`(승계 조건, 2/3) → `/owner/register`(은퇴 희망일, 3/3) → `/owner/matches` 순서로 진행한다. 청년은 `/successor` → `/successor/register`로 진입하며 제안·가일정은 `/offers/current`, `/succession/schedule`이다.
- 현재 새 화면은 예시 데이터와 메모리 상태로 동작한다. 새로고침하면 초기 예시로 돌아가며 서버 저장·실제 제안 전송·실제 승인 처리는 아직 연결하지 않았다.
- 사용자 요청에 따라 은퇴 희망일 등록 화면은 수락 후에도 날짜·빠른 선택을 사용할 수 있으며, ‘승계가 시작됐어요’ 안내나 잠금은 표시하지 않는다. 등록 초안과 수락한 승계 날짜는 별도 보관한다. 등록 초안을 고쳐도 기존 제안·가일정 날짜는 유지하고, 승계 날짜 변경 요청은 별도로 처리한다.
- 청년 등록의 희망 업종 선택지는 최신 사용자 요청에 따라 한식·양식·중식·일식·카페 순서로 표시한다. 복수 선택을 유지하며 초기 선택은 한식이다.
- 매칭 추천 카드의 청년 후보·적합도 점수·추천 이유는 추후 AI와 연결할 예정이다. 현재는 예시 후보 데이터를 사용하고 있으며 AI 연동은 구현하지 않았다.
- 매칭 카드는 펼치고 접을 수 있으며, 펼친 카드에는 경력 상세·준비 자금·대출 계획·희망 업종·희망 지역·근무 조건의 샘플 프로필을 표시한다. 최민재 카드도 같은 방식으로 상세 정보를 확인할 수 있다.
- 사장님의 제안 작성 화면은 가게 사진 선택·미리보기·변경·삭제와 ‘승계제안자에게 남길 말’ 직접 입력(최대 500자)을 지원한다. 사진·문구는 화면 이동 중 유지하고 받은 제안에서는 내용을 표시한다. 현재는 메모리 상태로만 보관하며 서버 파일 업로드 API는 아직 연결하지 않았다.
- 사장님 가게 정보는 빈 값에서 직접 등록한다. 이름·가게명·업종(한식/양식/중식/일식/카페)·지역은 필수이며 메뉴·상세 주소·개업 연도·사진은 선택이다.
- 승계 조건에서 인수 금액, 권리금·주방 설비·레시피·상호·간판·거래처·단골·운영 노하우의 복수 포함 항목과 기타 항목, 수습 3~12개월, 근무 시작·종료 시간, 새벽 근무 여부를 지정한다. 포함 항목을 고르지 않으면 예시 항목으로 대체하지 않는다.
- 매칭의 가게명과 제안 상세는 실제 입력한 가게 정보를 표시한다. 제안을 보내거나 수락한 시점의 조건을 보관하므로 이후 등록 초안 수정으로 이미 보낸 제안·수락한 조건이 달라지지 않는다. 청년 화면을 직접 열면 별도의 받은 제안 예시를 사용한다.
- 일정 역산과 안내문은 선택한 수습 개월 수를 사용한다. 시작·종료 시간이 같으면 제출을 막고, 종료가 시작보다 빠르면 다음 날 종료로 표시한다.
- 은퇴일 미정으로도 먼저 매칭을 둘러볼 수 있다. 제안 전송 시에는 기본 정보·금액·근무 조건·은퇴일을 다시 검증하고, 준비 기간은 백엔드의 `오늘 + (수습 개월 수 + 2개월) + 24일` 조건을 적용한다. 잘못된 값은 관련 입력 화면으로 이동할 수 있는 안내를 표시한다.

## 최신 화면 구조 변경 - 2026-11-07

- 최신 사용자 보완에 따라 온보딩에서 기본 정보와 역할별 조건을 미리 받는다. 이름·나이는 필수, 연락처·이메일은 선택이다. 사장님은 가게 업종·위치·판매 금액·함께 넘길 것 등을, 청년은 경력·자금·대출 계획·희망 업종·지역 등을 입력한 뒤 홈으로 이동한다. 사람 찾기·제안·신청을 자동 실행하지 않는다.
- 기본 메뉴는 홈·노포 찾기·AI 매칭·승계교육·마이의 5개 탭이다. 홈은 추천 가게와 서비스 소개, 노포 찾기는 대구 내 검색·업종 필터·가게 상세, AI 매칭은 조건 설정·비교, 승계교육은 제안 확인과 수락 후 과정, 마이는 개인 정보와 등록 정보 관리다.
- 사용자 확인에 따라 기존 **사장님 제안 → 청년 수락·거절** 방향은 유지한다. 청년 신청 → 사장님 승인으로 바꾸지 않는다. 백엔드도 역방향 신청 API를 새로 가정하지 않는다.
- 사장님 화면은 짧고 쉬운 문구, 큰 글씨·버튼, 적은 정보량을 우선한다. 탭 표시는 홈·가게보기·청년찾기·진행상황·내정보다. 청년 화면은 노포 탐색·조건 비교를 중심으로 구성한다. 어려운 조건과 상세 정보는 별도 화면이나 펼친 영역에서 확인하게 한다.
- 역할 선택 후 `/onboarding/profile`에서 시작한다. 사장님은 `/owner/shop?onboarding=1` → `/owner/terms?onboarding=1` → `/owner/register?onboarding=1`, 청년은 `/successor/register?onboarding=1`을 거쳐 홈으로 이동한다. 완료한 역할은 다시 선택해도 홈으로 간다. 온보딩을 마치기 전에는 홈·탭 진입 시 기본 정보로 돌아간다.
- 온보딩 이후 가게 정보 편집 저장은 `/my`, 청년 조건 편집 저장은 `/my`(매칭에서 들어온 경우 `/matching`)로 돌아간다. 선택한 가게의 매칭 확인 중 조건을 편집할 때 가게 ID를 유지한다.
- 주 화면 경로는 `/home`, `/shops`, `/shops/:id`, `/matching`, `/education`, `/my`, `/my/profile`이다. 내 정보에서 `/my/terms`, `/my/privacy`, `/my/about`으로 서비스 안내를 볼 수 있다. 약관과 개인정보 문구는 정식 정책 확정 전 안내이며 실제 법률 검토·운영 정책 확정을 대체하지 않는다. 기존 제안·교육 상세는 유지하고 하단 탭을 연결한다.
- 나이는 프런트 개인 정보의 문자열로 보관한다. 기존 서버에 사장님 나이 저장 필드가 확인되지 않았으므로 별도 DTO나 저장 API가 이미 있다고 가정하지 않는다.
- 홈·노포 목록·상세의 가게 분위기 사진은 로컬 CC0 이미지 3장을 사용한다. 실제 사용자가 올린 가게 사진과 구분하며, 출처·라이선스는 `docs/image-credits.md`에 보존한다.
- 노포 탐색·조건 비교는 현재 가게 예시 데이터와 메모리 상태를 사용한다. 실제 매장 검색 API, AI 모델, 개인 정보 저장 API를 이번 화면 재구성만으로 연동했다고 간주하지 않는다.

## 최신 API 통합 - 2026-11-08

- `origin/main`의 팀원 API 작업(`73dbe835`, PR #3)을 온보딩 작업 브랜치에 병합한다. UI와 서버 작업의 공통 조상은 `a52f34a`이며, 기존 온보딩 커밋 `de76dee`는 백업 브랜치 `backup/onboarding-before-sync-20261108`에도 보존한다.
- 온보딩과 5개 탭은 유지하며, 메모리 전용 `DemoContext`·`SuccessionContext`를 제거하고 서버 `AppContext`를 사용한다. 역할 선택 뒤 기본 정보 화면에서 사용자가 입력한 이름·역할로 개발용 로그인을 한다. 실제 카카오·휴대폰 인증은 미연동이다.
- 가게·청년 정보는 저장 API 성공 뒤 홈으로 이동한다. 실패하면 오류를 표시하며 완료된 것처럼 처리하지 않는다. 사장님의 은퇴 희망일은 서버 필수 값이므로 날짜 미정 상태로 서버 저장하지 않는다. 수습 개월 수 + 2개월 + 24일 이후 날짜를 안내·검증한다.
- 청년은 대출 예정 금액과 새벽 근무 여부도 입력한다. 나이는 서버 범위 15~80세로 저장하며, 사장님 나이는 확인된 서버 필드가 없어 브라우저 탭의 계정별 보조 정보로 보관한다. 연락처·이메일도 같은 방식이며 이름은 서버 로그인 정보를 읽기 전용으로 사용한다.
- 교육 탭의 제안 목록·승계 요약·진행률은 서버 응답을 표시한다. 개별 제안은 `/offers/current?offer=ID`로 확인한다. 사장님 후보 목록, 제안 전송·수락·거절, 일정·체크리스트·계획·수습·납입은 팀원 API 코드를 유지한다.
- 노포 탐색과 홈 추천, 청년의 예시 가게 비교는 기존 둘러보기 자료를 유지한다. 실제 노포 검색·청년 가게 매칭 API가 연결된 것으로 안내하지 않는다. 가게 사진 업로드, 승계 계획 대화의 서버 저장, 사장님 직접 수습 완료 API는 여전히 별도 작업이다.
- 등록·수정 폼과 역할별 큰 글씨·쉬운 문구를 보존하며, 실제 배포 서버에 테스트 데이터를 쓰지 않고 가짜 API 응답으로 통합 동작을 검증한다.

## 실제 백엔드 소스 확인 (기존 기록)

사용자가 제공한 저장소: https://github.com/donghyun-03/mullyeobatgi-backend

구체적인 DTO와 제약, 소스 경로는 [backend-contract.md](backend-contract.md)에 보존했다.

PDF와 달리 실제 소스에는 DTO와 API 구현이 있다. 구현 시 PDF의 개요와 함께 실제 소스를 확인한다.

- 서버 역할 enum은 `OWNER`·`YOUTH`다. 프런트 `successor`를 서버에 그대로 보내지 않는다.
- 인증 토큰은 `Authorization: Bearer {token}`으로 보낸다. 개발 로그인은 `POST /api/auth/dev-login`에 이름·역할을 보내고 토큰과 내 정보를 받는다.
- 가게 저장은 은퇴일만으로 완료할 수 없다. `name`, `category`, `district`, `askingPrice`, `retireDate` 등 필수 정보가 필요하다. 아직 정하지 않은 은퇴일은 서버 저장 조건을 충족하지 않는다.
- 청년 프로필은 `experience`, `fundsReady`, `loanPlanned`, `loanAmount`, `preferredCategories`, `preferredDistricts` 등을 사용한다. 경력 enum은 `NONE`, `UNDER_1Y`, `ONE_TO_3Y`, `OVER_3Y`다.
- 실제 역산은 `TimelinePlanner`를 따른다. 인수 시작일은 은퇴일에 1일을 더한 뒤 2개월 전, 수습 시작일은 인수 시작일에서 수습 기간 전, 계획 동의 기한은 수습 시작 12일 전, 체크리스트 기한은 계획 동의 기한 5일 전이다. 월요일 보정은 하지 않는다.
- 기본 은퇴일 `2027-08-31`과 수습 6개월의 결과: 체크리스트 `2026-12-15`, 계획 `2026-12-20`, 수습 `2027-01-01`~`2027-06-30`, 인수 시작 `2027-07-01`.
- `ShopService`의 은퇴일 최소 조건은 오늘에 수습 개월 수 + 2개월 + 24일을 더한 날짜다. 기본 6개월 수습일 때 ‘6개월 뒤’는 그대로 저장할 수 없으므로 실제 저장 연동에서는 검증과 조율이 필요하다.
- 실제 제안 응답 기한은 14일이다. 화면 예시에서도 이 기간을 기준으로 안내한다.
- 배포 서버 주소·인증 연동을 확인하기 전에는 예시 화면을 실제 서버 저장이 완료된 것처럼 안내하지 않는다.
